# api

Backend do SYNQ OS (regras de negócio, autorização, integração com o SAP, eventos de campo (online e fila offline), geração de PDF e e-mail). Node + TypeScript, [Hono](https://hono.dev) para as rotas, [Drizzle](https://orm.drizzle.team) sobre Postgres (Supabase) e [zod](https://zod.dev) para validar a entrada.

Ver a [especificação](../base/.design/especificacao.md) para escopo, contratos e decisões técnicas, e o [banco](db/README.md) para o schema.

## Como rodar

```bash
cd api
pnpm install
pnpm typecheck
pnpm test        # roda tudo num Postgres embutido (PGlite), sem Supabase
pnpm dev         # precisa das variáveis abaixo e de um Supabase (nuvem ou local)
pnpm dev:local   # sem Supabase: banco em memória (PGlite), auth e arquivos em memória, SAP simulado e usuários de exemplo
pnpm pdf:exemplo # grava ordens-exemplo.pdf: OS no layout impresso pelo SAP, com texto, para testar a importação por PDF
```

**Modo local (`pnpm dev:local`, [`src/local.ts`](src/local.ts)):** a `api` inteira num só processo, para desenvolver o `web` e o `mobile`. Cria as equipes Serviços Especiais, Instrumentação e Laboratório Químico e um usuário por perfil (e as duas supervisoras), todos com a senha `synqos123`. O login é o e-mail institucional, no padrão primeiro nome e último sobrenome com domínio `@empresa.com.br` (`admin`, `sandra.supervisora`, `saulo.supervisor`, `tiago.tecnico`, `tais.tecnica`, `tomas.tecnico`); a `api` os lista ao subir. Lê as 11 OS das fixtures pelo simulador do SAP, cria um catálogo de serviço fictício (materiais de 4 serviços, [`src/db/seed/catalogo-demo.ts`](src/db/seed/catalogo-demo.ts)) e serve as fotos e os PDFs em `/arquivos-locais`. Tudo some quando o processo termina; nunca é para produção.

Variáveis de ambiente (todas lidas em [`src/config.ts`](src/config.ts)): `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_JWT_SECRET`, `SAP_API_URL`, `SAP_API_TOKEN`, `SAP_SIMULADO` (`true` liga o simulador em `/sap-simulado`), `SAP_LEITURA_INTERVALO_MIN` (padrão 15), `RH_SIMULADO` (`true` liga o registro de funcionários simulado em `/rh-simulado`), `RH_API_URL`, `RH_API_TOKEN`, `RH_AVISO_TOKEN`, `RH_AVISO_URL` e `RH_LEITURA_HORA` (padrão 3), `SMTP_URL`, `EMAIL_REMETENTE`, `PAINEL_URL`, `PORT` (padrão 3333). Com `SAP_SIMULADO=true`, aponte `SAP_API_URL` para `http://localhost:3333/sap-simulado` e `SAP_API_TOKEN` para o token que o simulador exige.

Na subida ([`src/servidor.ts`](src/servidor.ts)) a `api` aplica as migrações sob trava de sessão do Postgres, carrega os dados iniciais, preenche o extrato da gamificação a partir do histórico (só enquanto o extrato está vazio, numa transação só; se falhar, nada é gravado e a próxima subida tenta de novo), grava no bucket `gamificacao` as imagens da carga que faltarem, inicia o executor de tarefas e só então abre a porta; `GET /saude` responde depois disso.

## Teste com Supabase real

O que não dá para provar com as versões em memória: Auth, Storage e Postgres de verdade. Roteiro com um projeto Supabase de teste (dados só fictícios):

1. **Projeto Supabase** (supabase.com, plano gratuito). Em *Project Settings*: a URL do projeto (`SUPABASE_URL`), a chave `service_role` (*API Keys*; `SUPABASE_SERVICE_ROLE_KEY`) e a string de conexão do Postgres (*Database › Connection string*; `DATABASE_URL`). Use a conexão **Session pooler** (porta 5432 do pooler) ou a direta, nunca a Transaction pooler (6543): as migrações usam trava de sessão (`pg_advisory_lock`). A conexão direta é só IPv6; sem IPv6, use o Session pooler.
2. **`.env` na raiz** (copie de `.env.example`) com essas três variáveis. `SUPABASE_JWT_SECRET` só é preciso se o projeto usa o segredo legado (HS256); com chaves assimétricas a `api` confere o token pelo JWKS do projeto.
3. **Subir a `api`**: `cd api && pnpm dev` (lê o `.env` da raiz). Ela aplica as migrações, carrega os 8 modelos de APR, cria os 6 buckets privados (`fotos`, `assinaturas`, `pdfs`, `importacoes`, `documentos`, `gamificacao`) e abre a porta; `curl localhost:3333/saude` deve dar `{"banco":"ok"}`. Com `SAP_SIMULADO=true` e `SAP_API_URL=http://localhost:3333/sap-simulado`, as OS do simulador entram em até 15 minutos (ou pelo botão "Ler agora").
4. **Primeiro admin**: `pnpm admin:criar -- --email admin@empresa.com.br --matricula adm --nome "Administrador" --senha "senha-inicial-123"` (a conta nasce com senha provisória). O e-mail é o login; a matrícula só identifica a pessoa. Se o banco já tinha usuários do tempo do login por matrícula, rode `pnpm usuarios:migrar-emails` (mostra o que mudaria) e depois `pnpm usuarios:migrar-emails -- --aplicar`.
5. **Subir o `web`**: `cd web && pnpm dev`, entrar em http://localhost:3000 com o e-mail do admin (será pedida a senha nova) e, em *Equipes e usuários*, criar a equipe (centro de trabalho `SERV_ESP`, o das OS do simulador), dois técnicos (um deles definido como supervisor da equipe) e, se quiser, outro administrador.
6. **Roteiro de conferência**: o técnico faz a APR aprovada → executa (pausa, foto, assinaturas) → encerra; no Supabase, conferir as linhas em `evento_campo`, `apr`, `execucao` e os arquivos nos buckets; o supervisor dá ciência; o admin exporta a planilha; repetir com uma APR bloqueada e ver o alerta (e o e-mail, se `SMTP_URL` estiver configurado).
7. **Docker**: com o `.env` preenchido, `docker compose up --build` (api em 3333, web em 3000) e repetir o roteiro. Com um Supabase local (`supabase start`), use `host.docker.internal` nas URLs do `.env`.

Pode rodar de novo sem duplicar.

`pnpm demo:popular` (com a `api` já iniciada uma vez e o `.env` apontando para o banco) cria dados **fictícios** para testar os fluxos: equipes, usuários (Saulo Supervisor, Tomás Técnico, Tânia Técnica, Tadeu Técnico, e os que faltarem, com e-mail `nome.sobrenome@empresa.com.br`), locais (alguns críticos, de clientes como Vale e Suzano) e 30 OS em todos os estados: liberadas (algumas atrasadas, uma reprogramada), em execução (uma em pausa), pendentes (APR bloqueada com fotos, bloqueada por condição pessoal, suspensa, interrompida por risco com OS de apoio), encerradas com e sem ciência (com PDF), uma execução esquecida há mais de 12 h, uma OS de apoio cancelada pelo admin e uma corretiva urgente lida do SAP. Todas as OS, menos as de apoio, têm origem `sap`, como se tivessem vindo da leitura do SAP. Tudo passa pelas regras da `api` (`processarEventos`), com a hora de cada evento no passado. Não duplica: se já houver OS `5100xxx`, não faz nada. O código está em [`src/db/seed/demo.ts`](src/db/seed/demo.ts) e é coberto por `test/demo.test.ts`.

## Convenções (valem para todas as rotas)

- **Autenticação:** `Authorization: Bearer <JWT do Supabase>`; sem token válido é `401`, perfil sem permissão é `403`. Com a senha inicial só `/me` e `/auth/trocar-senha` respondem (`403` `senha_provisoria`). Usuário desativado recebe `401` `acesso_revogado`, exceto em `PUT /arquivos/{id}` e `POST /eventos`, para a fila offline pendente subir; depois do envio a conta é revogada.
- **Perfis:** só `tecnico` e `admin`. Supervisor não é perfil: é o técnico que consta em `equipe.supervisor_id` (`equipes_supervisionadas` em `/me`); faz tudo que o técnico faz e mais a supervisão (ciência, reprogramar, alertas, indicadores, OS de apoio) das equipes que supervisiona. O admin só gerencia (importa, exporta, edita modelos, cancela OS, vê todas as equipes) e não executa OS. A migração `0007` converteu os dados antigos.
- **JSON em snake_case**, erros `{erro: {codigo, mensagem}}` (`422` `validacao` para campo inválido), listas `{<nome>: [...], pagina, tamanho, total}` com `?pagina=1&tamanho=50` (máximo 200). Datas `AAAA-MM-DD`, instantes ISO 8601; "dia" é em `America/Sao_Paulo`.
- **Arquivos:** `PUT /arquivos/{id}` (multipart `arquivo`, `tipo` = `foto`, `assinatura` ou `pdf`) com o id gerado no cliente; reenviar o mesmo id e conteúdo não tem efeito, conteúdo diferente é `409`. O `pdf` (documento de evidência, até 10 MB, bucket `documentos`) é conferido pelo conteúdo: precisa começar como um PDF, senão `422` `tipo_de_arquivo`. Os eventos referenciam o arquivo pelo id (`arquivo_id`, ou o próprio `id` da evidência).
- **Evidências: foto ou PDF.** Cada evidência dos eventos leva `tipo` (`foto`, o padrão, ou `pdf`) e, no PDF, `nome` (o nome do arquivo anexado). O item reprovado exige o que o modelo diz em `evidencia` (`foto`, `texto` ou `pdf`); foto e PDF a mais são sempre aceitos, e o PDF não substitui a foto exigida. O encerramento e a interrupção exigem ao menos uma foto e aceitam até 10 fotos e 5 PDFs. As respostas trazem os dois separados: `fotos` (`{id, foto_path, capturada_em, latitude, longitude}`) e `documentos` (`{id, arquivo_path, nome, capturada_em}`). O PDF da OS lista os documentos anexados à execução (o arquivo fica no sistema), e o e-mail de bloqueio leva o link de cada um.
- **Só `POST /eventos` escreve APR e execução.** Resposta sempre `200`: `{confirmados, alertas, aprs, os, rejeitados: [{id, codigo, mensagem}], pendentes: [{id, codigo, mensagem}]}`. `rejeitados` não adianta reenviar; `pendentes` (arquivo ou evento anterior ainda não chegou) ficam na fila do cliente. Evento que vem da fila offline (chegou mais de 60 s depois de `ocorrido_em`) é aplicado mesmo quando conflita com o que mudou no servidor, e vira `alerta`; online, o mesmo conflito é recusado.

Também ao subir e de hora em hora, e sem passar pela fila de tarefas, ele confere as ausências (`conferirAusencias`, em [`src/dominio/ausencia.ts`](src/dominio/ausencia.ts)): cancela o pedido parado cuja data de retorno chegou, aplica o início das ausências que começaram e avisa o supervisor das que venceram; é idempotente.

## Onde a implementação difere da especificação

- `POST /modelos-apr/{codigo}/versoes` recebe `riscos[]` e itens com `risco_ordem` no lugar de `grupo` (o schema tem a entidade risco); todos os campos são opcionais e, se omitidos, copiam a versão anterior. Num código novo, `copiar_de` parte do conteúdo de outro modelo e `versao` diz o número da primeira versão. Há também `GET`, `PUT` e `DELETE` de versão para o editor.
- Os modelos, a orientação de cada um e a tabela de atividades são escritos só pelo admin (a Segurança do Trabalho define o conteúdo, mas não usa o sistema).
- `DELETE /modelos-apr/{codigo}` exclui o modelo inteiro: apaga o que nunca foi publicado, com a orientação, e **arquiva** (`modelo_apr.arquivado_em`, migração `0006`) o que já foi, porque APRs, PDFs e a APR offline pendente apontam para as versões. O arquivado sai das listas, de `versoes/publicada`, da escolha do modelo e da cópia offline, mas a APR respondida nele ainda é aceita, e a orientação fica guardada. `POST /modelos-apr/{codigo}/restaurar` desfaz, e o modelo volta com a orientação.
- `os` ganhou `cancelada_em`, `cancelada_por` e `justificativa_cancelamento` (migração `0002`), para guardar a justificativa do cancelamento da OS de apoio.
- `POST /eventos` devolve `rejeitados` e `pendentes` além dos campos da especificação.
- **O técnico não sabe o que é eliminatório.** Só o admin recebe `tipo`, `resposta_bloqueante` e `evidencia` dos itens: o técnico (e o supervisor, que é um técnico) recebe o modelo (`GET /modelos-apr/{codigo}/versoes/{versao}` e a cópia de `POST /sync/pull`) sem esses campos, o detalhe da OS (`GET /os/{id}`, `GET /os/{id}/aprs`) sem `tipo`, `evidencia`, `resposta_bloqueante` e `alerta_marcado` e o dashboard (`GET /aprs/resumo`) com `itens_que_bloqueiam`, `alertas_registrados` e `totais.alertas` nulos. Do que reprovou ele só fica sabendo depois de validar.
- `POST /aprs/avaliar` (técnico) recebe a APR inteira menos as fotos (o payload de `apr_concluida` sem `evidencias`, com `os_id` obrigatório) e devolve `{resultado: "aprovada" | "bloqueada", reprovados: [{item_id, texto, evidencia}]}`. É como o aparelho descobre, ao concluir, quais itens reprovaram e a evidência de cada um. Antes do resultado confere tudo o que o registro confere (OS da equipe, participantes com assinatura, respostas completas, "NA" com observação): a recusa (`422`, `404` para OS de outra equipe, `409` para OS em execução ou encerrada) nunca depende de a APR reprovar. A aprovada não é gravada. A bloqueada é registrada na hora, pelo mesmo caminho dos eventos (OS `pendente`, alerta e e-mail ao supervisor), para que descobrir o que reprova sempre deixe registro; validar de novo a mesma APR devolve o que ficou gravado. A evidência dos reprovados chega depois, no `apr_concluida` da mesma APR, que online a exige inteira (`evidencia_faltando`) e não muda as respostas.
- **Representante da equipe** ([representante.md](../representante.md), migração `0026`): toda equipe tem um representante (`equipe.representante_id`), um técnico ativo e liberado dela que não é o supervisor; a `api` escolhe o mais antigo (`garantirRepresentantes`) até o supervisor ou o admin designar outro com `PUT /equipes/{id}/representante` `{usuario_id}` (`422` `representante_invalido`). Ele assume a supervisão quando o supervisor tem uma ausência em curso ou vencida (`ausencia`) ou passa 3 dias sem usar o sistema (`inatividade`, `usuario.ultima_atividade_em`, anotada por `autenticar()` no máximo a cada 5 min): `autenticar()` soma essas equipes a `equipesSupervisionadas` (e as lista em `equipesRepresentadas`), então toda permissão de supervisão vale para ele, menos registrar a própria ausência como supervisor (`ehSupervisorTitular`), mexer na ausência do supervisor e responder ao próprio pedido. `GET /me` traz `equipes_representadas`; `GET /equipes/{id}` traz `representante` e `representacao`. A passagem de comando (`equipe.representacao_desde`/`representacao_motivo`) é gravada por `sincronizarRepresentacao` (depois de cada ato da ausência, quando o supervisor volta e na tarefa de hora em hora) e gera os alertas `representacao_iniciada` e `representacao_encerrada` (para o representante e o supervisor, com `equipe_id`); os alertas da equipe também vão ao representante no comando.
- **Usuário ausente** ([ausencia.md](../ausencia.md), migração `0025`): a pessoa com uma ausência `confirmada` que já começou (do `inicio`, 0h em São Paulo, até o retorno ser confirmado ou a ausência encerrada) só visualiza. `autenticar()` carrega a ausência em `UsuarioAutenticado.ausencia`, e toda rota que altera (`POST`, `PUT`, `PATCH`, `DELETE`) responde `403` `usuario_ausente`, menos as que ligam `permitirAusente`: `POST /auth/sair`, `POST /auth/trocar-senha`, `PATCH /alertas/{id}`, `POST /gamificacao/avisos/vistos`, `POST /sync/pull`, `PUT /arquivos/{id}`, `POST /eventos` (só aceita o que aconteceu antes do início: o resto volta em `rejeitados` com `usuario_ausente`) e as ações da própria ausência (`pedir-fim`, `confirmar-retorno`, `prorrogar` e `encerrar`, estas duas só para o supervisor cuidar da própria ausência: sobre a da equipe, `usuario_ausente`). Ela não termina sozinha: depois do retorno fica `vencida` (a situação sai das datas; só `pedida`, `aguardando_confirmacao`, `confirmada`, `encerrada`, `recusada` e `cancelada` são gravadas). Efeitos: no início, a execução aberta da pessoa é suspensa e as OS reservadas a ela voltam para a equipe toda (ato `inicio`, de onde a linha do tempo da OS tira "Reserva desfeita: ausência de <nome>"); `PUT /os/{id}/responsavel` recusa o ausente (`422` `responsavel_ausente`) e a APR também (`participante_ausente`). `GET /me` traz `ausencia` e as listas de pessoas (`GET /usuarios`, `GET /usuarios/{id}`, `GET /equipes/{id}`, `usuarios` do `POST /sync/pull`) trazem `ausencia` em cada pessoa. O pedido de fim antecipado guarda a data pedida em `ausencia.fim_pedido_data` e `fim_pedido_em`. Os nove alertas novos (`ausencia_pedida`, `ausencia_aprovada`, `ausencia_recusada`, `ausencia_registrada`, `ausencia_fim_pedido`, `ausencia_fim_respondido`, `ausencia_alterada`, `ausencia_vencida`, `ausencia_cancelada`) não têm OS: apontam para a ausência (`ausencia_id`, `usuario_alvo_id`, `usuario_alvo_nome`, `ausencia_equipe_id`). Cada ato vira `ausencia.<ato>` na auditoria. Sem e-mail: só o sino.
- **Liberação de acesso** (`usuario.liberacao`: `liberado`, `pendente`, `recusado`): o admin cria usuários já `liberado`; o supervisor só cria técnicos em equipes que supervisiona, e a conta nasce `pendente` (com `criado_por_id`). O pendente só passa em `GET /me`, `PUT /me/treinamento` e `POST /auth/trocar-senha` (opção `permitirPendente` de `autenticar()`); o resto é `403 aguardando_liberacao`. O recusado leva `403 acesso_recusado` no login (a mensagem traz o motivo) e `401 acesso_revogado` nas demais rotas. `liberar` e `recusar` só valem para `pendente` (senão `409 nao_pendente`); o admin exclui o recusado pelo `DELETE` e o e-mail e a matrícula voltam a ser usáveis. `GET /me` e os usuários trazem `liberacao`, `criado_por_id`, `criado_por_nome`, `criado_em` (nulo nas contas anteriores à migração `0010`), `liberado_em` e `recusa_motivo`.
- `GET /usuarios` e `GET /equipes` servem a todos os perfis (a lista de participantes da APR precisa dos colegas); só o admin vê e-mail e usuários desativados. O e-mail serve de busca para todos, mas só o admin o recebe na resposta.
- Busca global (não está na especificação): `busca` procura, sem diferenciar maiúsculas nem acentos, no nome, matrícula, cargo, e-mail e CREA do usuário; no nome e centro de trabalho da equipe; e no número da ordem, título, código do local, número da nota e cliente da OS. Cada lista traz só o que tem o texto em algum desses campos. Regras em [`src/dominio/busca.ts`](src/dominio/busca.ts).

- **Cadastro pelo registro de funcionários:** `POST /usuarios` recebe só `{matricula, email, perfil?, equipe_id?, senha_inicial}` (nome, cargo e CREA vêm do registro), `PATCH /usuarios/{id}` não aceita mais nome, e-mail, cargo nem CREA (`422`, e `403` para o supervisor, que só cancela o cadastro pendente) e há `POST /usuarios/{id}/atualizar-do-registro`. A migração `0019` cria `funcionario_simulado` e `leitura_rh`, as colunas `usuario.situacao_registro` e `registro_conferido_em`, os tipos de tarefa `leitura_rh` e `conferencia_rh`, a entidade de auditoria `rh` e deixa `auditoria.ator_id` aceitar nulo (o ator de sistema "Registro de funcionários"). A `leitura_rh` tem a coluna `dia`, com índice único, que garante uma leitura agendada por dia.
- **O simulador do SAP passou para o banco:** a migração `0020` cria `ordem_sap_simulada`. `POST` e `PATCH /sap-simulado/ordens` saíram do contrato e viraram a gestão em `/sap-simulado/gestao`.
- **O técnico escolhe o modelo da APR** (decisão de 14/10/2026, questão 58): não há atribuição automática. A migração `0021` cria `orientacao_modelo_apr` (uma linha por código de modelo, fora do versionamento: `descricao`, `exemplos`, `palavras_chave`) e tira `atividade.modelo_apr_codigo`; a carga inicial grava a orientação dos 8 modelos ([`src/db/seed/orientacoes-modelos-apr.ts`](src/db/seed/orientacoes-modelos-apr.ts)) só onde ainda não há. `GET /os/{id}/modelos-apr` devolve `{recomendado, modelos: [{codigo, versao, titulo, descricao, exemplos, encontradas}]}`: a versão publicada mais recente de cada modelo não excluído e o recomendado pela leitura da OS (palavras-chave no título, peso 3; na descrição do serviço do catálogo, peso 2; na descrição da OS, peso 1; cada palavra conta uma vez, sem acento nem maiúsculas; com 4 letras ou mais vale também como começo de palavra; empate no topo ou nada achado não recomenda nenhum). As palavras-chave não vão nessa resposta, só o que foi achado (`encontradas`); quem não vê a equipe da OS recebe `404`. Regras em [`src/dominio/recomendacao-apr.ts`](src/dominio/recomendacao-apr.ts). O `PUT /modelos-apr/{codigo}/orientacao` grava na auditoria `modelo_apr.orientacao`. No `POST /sync/pull`, cada OS traz `escolha_do_modelo` `{recomendado, encontradas: [{codigo, palavras}]}` e cada modelo traz `orientacao` `{descricao, exemplos}`. `POST /aprs/avaliar` e `apr_concluida` aceitam qualquer modelo publicado. Saíram: `modelo_apr_codigo` de `GET /os/{id}`, `atividades_total` de `GET /modelos-apr`, as atividades e as OS abertas de `GET /modelos-apr/{codigo}/uso`, o `?substituto=` do `DELETE`, os filtros `?modelo` e `?sem_modelo` de `GET /atividades`, o aviso "Atividade sem modelo de APR" da leitura e da importação (o código da atividade vai sempre para a OS; o código novo é cadastrado em `atividade` com o título da ordem como descrição) e os indicadores de APRs em OS sem modelo ligado (`/aprs/resumo`) e de atividades sem modelo (pendências de `/indicadores/geral`). Na conferência do PDF, cada ordem traz `atividade: {codigo, descricao} | null`. Testes em `test/recomendacao-apr.test.ts` e `test/modelos-apr.test.ts`.

## Não coberto

- Execução contra o Supabase real (Auth e Storage foram escritos pela API REST e só testados com versões em memória) e contra um Postgres fora do PGlite.
- As imagens Docker não foram construídas nem executadas (sem Docker na máquina de desenvolvimento): o que foi verificado é a instalação só com dependências de produção e a importação da aplicação nesse conjunto de arquivos.
- Modo offline do lado do app (o `POST /sync/pull` já existe).
